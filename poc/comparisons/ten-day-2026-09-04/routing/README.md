## The two measurements

They are separate on purpose, because system-design.md §320 says the graph is
**built** on a dev machine and **served** on an 8 GB box.

| | Build | Serving |
| --- | --- | --- |
| Compose profile | `build` (`motis-build`) | `serve` (`motis`) |
| Memory | uncapped, by design | `mem_limit: 8g`, **do not raise** |
| Measured | 40 s wall, 3,738.6 MB peak RSS, 910.8 MB graph | 937.8 MB steady, 1,129.5 MB peak under load |
| Verdict | fine on this machine | **fits, at 13.8 % of the cap** |

Raising the 8 GB cap would produce a number that is true only on this desk. If
Israel had not fitted, `fits_in_8gb: false` was the correct result to record —
it is a finding about §331's cost tiers, not a knob.

## Running it

Everything assumes Docker Desktop is up and `poc/data/` holds the feeds listed
in `poc/data/manifest.json`.

```
# 1. Build the graph. Uncapped. Takes about a minute on a 16-core box.
#    Runs long enough that it should be launched and left alone.
python poc/routing/run_import.py

# 2. Start the capped server.
docker compose -f poc/docker-compose.yml --profile serve up -d motis

# 3. Run the 25 journey cases.
python poc/routing/run_corpus.py                          # primary
python poc/routing/run_corpus.py --profile generous-walk  # labelled variant

# 4. Does it still fit under concurrency, and what does it hold at rest?
python poc/routing/stress_serving.py --workers 16 --seconds 120
python poc/routing/measure_steady.py --seconds 150

# 5. Assemble the deliverables.
python poc/routing/write_result.py     # -> results/poc-2.json
python poc/routing/render_h3.py        # -> results/journeys-h3-review.md
python poc/poc_status.py --write
```

`diagnose_no_route.py` is not part of that sequence. It exists to answer *why*
a case returned nothing, and is worth re-running whenever a new one does.

## Three traps that cost time, so they do not cost it twice

None of these are findings about MOTIS or about Israeli data. They are Windows
Docker configuration, and they are written up here so the next person recognises
them in seconds.

1. **`unable to import: resize error`, 3 seconds in, all `.bin` files zero
   length.** The MOTIS data directory was bind-mounted from the Windows
   filesystem. MOTIS grows memory-mapped files with `ftruncate` + re-`mmap`, and
   Docker Desktop's filesystem-sharing layer cannot do that. The data directory
   **must** be a named volume. This one generalises beyond Windows: the shipped
   graph artifact needs a real filesystem, not a shared folder or an
   object-storage FUSE mount.

2. **Containers capped at ~16 GB on a 32 GB machine.** WSL2's default ceiling is
   about half of host RAM, and it applies to the uncapped build too. Raised in
   `%USERPROFILE%\.wslconfig`. ADR 0004 requires this raise *before* any import
   failure is blamed on MOTIS. (Here it turned out not to matter — the build
   peaked at 3.7 GB — but it was done first, so the number means what it says.)

3. **Docker Desktop refusing to start at all**, backend crash-looping on a stale
   `userAnalyticsOtlpHttp.sock` that Windows would not delete by any means.
   Renaming `%LOCALAPPDATA%\Docker\run\` aside let it be recreated.

## What the compose file got wrong, and why

The Wave 0 scaffold had `command: ["import"]` and `command: ["server"]`. The
verbs are right — MOTIS v2 really does have `config`, `import` and `server` —
but the image declares **no entrypoint**, so a compose `command:` replaces argv
entirely and Docker tried to exec a binary named `server`. `/motis` has to be
`argv[0]`, and both subcommands take flags:

```
/motis import -c /config.yml -d /data
/motis server -d /data
```

`motis import` writes a copy of the config into the data directory, so the
serving container needs only that directory — which is why it no longer mounts
`./data` at all. That absence is deliberate: it is what "ship the artifact"
means.
