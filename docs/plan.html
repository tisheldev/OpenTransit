Product plan · Initial PRD

OpenTransit Israel

An open-source journey planner for Israeli public transport — buses, Israel Railways, light rail, walking and transfers. Fast, ad-free, privacy-conscious, and built on public data. The plan below is gated: nothing gets built until the data proves it can be built. As of 28 August 2026 the schedule data is verified open and the Ministry's realtime feed is the one thing standing between this plan and a working app. The first thing built is not an app — it is a backend fast enough that a client only has to render it.

01

One question, answered fast

The product exists to answer a single question: what is the best way for me to get there using public transportation? Open app, pick a destination, see routes, follow the journey. It is optimised for the same trip made every day, not for tourism.

The underlying network already exists, and so does most of the data. The opportunity is a better interface and a better engineering layer on top of Israel's open transport ecosystem.

Speed is a feature

Startup under 2s perceived. Search results under 500ms. Route request target under 2s. Saved places open instantly.

Honest realtime

Scheduled, predicted, delayed, cancelled and unknown are five different states. Uncertain data never gets to look authoritative.

No hidden lock-in

No proprietary transport API where an open one exists. Every external service sits behind a replaceable interface.

02

Phase 0 is a gate, not a warm-up

Hard rule
Frontend product development does not begin until Phase 0 passes.

Phase 0 answers one question: can an independent application actually obtain enough usable Israeli transport data to reproduce core journey planning? It deliberately has almost no UI — a CLI, a Swagger page or an ugly debug endpoint is enough. Finding a fatal problem here is a successful outcome; finding it after months of app work is not.

04

Six proofs to clear

Each proof has an explicit pass bar and an explicit stop condition. They run in order, because each one consumes the output of the last.

POC-1

Static nationwide schedule data verified open

Download, extract and parse the Ministry of Transport GTFS: agencies, routes, trips, stops, stop times, calendars and shapes. Load it, query it, and verify known lines and stations in Tel Aviv, Jerusalem, Haifa, Israel Railways and several bus operators.

Source: MOT GTFS

Pass The latest official dataset refreshes automatically — no manual editing anywhere in the loop.

Stop Nationwide schedule data cannot be consumed legally and reliably.

POC-2

Journey routing on Israeli data unblocked

Turn that GTFS into a routing graph with an existing open engine rather than hand-writing transit routing. MOTIS first, OpenTripPlanner as the alternative, self-hostable either way. Transitous already runs MOTIS with Israeli GTFS coverage — useful as reference architecture and as a comparison implementation.

MOTIS / OpenTripPlanner10 test journeys

Pass 9 of 10 representative journeys return reasonable, usable routes — including bus↔train, a transfer, late night, a service-day boundary, and one journey with no sensible transit route at all. Checked by hand against Moovit, Google Maps and BetterRail; logical correctness matters, exact agreement does not.

Stop No self-hostable open engine routes Israeli GTFS reliably. Try another engine — do not start the app.

POC-3

Realtime arrivals, matched to schedule gated on MOT

The riskiest proof. Pull SIRI-SM predictions, identify route, vehicle, trip and predicted stop, then reconcile each realtime trip against its static GTFS trip. Vehicle positions map to a route and a point on the map. That reconciliation layer is our own code and gets tested hardest.

MOT SIRI (production)Open Bus Stride (prototype)

Pass Route 18 shows scheduled 18:04, realtime 18:11, delay +7 min — and the trip identity is provably the same trip in both feeds.

Also required Either direct Ministry SIRI access, or another source whose terms and sustainability are acceptable for production. Open Bus is fine for experiments; depending on a volunteer service permanently has to be a deliberate architectural decision, not an accident.

Stop No sustainable realtime source. A schedule-only planner could exist, but it would not be this product.

POC-4

Service alerts gated on MOT

Read the GTFS-Realtime Service Alerts feed, decode the protobuf, resolve the affected routes, stops and trips, and attach the alert to a planned journey that touches them.

GTFS-RT Service Alerts

Pass A live or recent alert parses and links to real transport entities — “Route 18 does not serve Arlozorov A/B, 18:00–21:00”.

POC-5

Address and place search unblocked

Nobody types coordinates. “Dizengoff Center” has to become 32.075, 34.774, and “HaShalom Station” has to land on the right platform area. Hebrew and English, street addresses, stops, stations, major POIs and current GPS position.

OSM-derived geocoder

Pass 20 representative Israeli queries resolve well enough to start routing.

Constraint Public Nominatim is for experiments only — 1 request/second and no client-side autocomplete. Production needs a hosted or self-hosted geocoder.

POC-6

One end-to-end journey partly gated

The actual acceptance test. A single command chains every proof together: address search → coordinates → transit routing → GTFS journey → realtime enrichment → alert enrichment → journey response.

Phase 0 acceptance

Pass route --from "Dizengoff Center" --to "Technion" --depart-now returns a real multi-modal journey. It does not have to look good. It has to be real.

07

The backend is the product first

No client work begins until the API is finished, deployed and fast. Every client is a thin renderer over the same endpoints, and speed is decided entirely on the server — a client cannot make a slow API feel fast, but a fast API makes an ordinary client feel excellent.

The one rule
No request on the hot path may make a call that leaves the machine.

Journey planning, departures, place search and realtime enrichment are answered from memory or from a process on loopback. Nothing on the hot path talks to Postgres, to object storage, to MOT, or to another availability zone. Everything slow — feeds, graph builds, SIRI polling, archiving — runs on a schedule, and its only output is a data structure the hot path reads with a pointer dereference.

Measured at the API process. The PRD's "under 2 seconds" is a client target; these are the numbers the backend is built against.

Two things worth noticing: the jump from nothing to a working public service is about $40, and the expensive jump is the one after it, because redundancy means buying a second of everything. And the thing that actually gates this project cannot be bought at any price — the MOT key is free, and no budget makes it arrive sooner.

Why free-to-use is sustainable

The expensive artifact — the routing graph — is built once and shared by everyone, so cost is nearly flat in users. Ten thousand daily users at five requests each is 0.6 req/s average with commute peaks around 20–30, which one 8 GB box absorbs without noticing. A journey response is 3–5 KB compressed, so 50k requests a day is about 7.5 GB of egress a month, most of it served by Cloudflare and never reaching the origin.

Running cost is roughly $40–70/month whether the service has 100 users or 50,000. The only thing that truly scales with popularity is map tiles — and PMTiles on R2 removes that bill by construction, because R2 charges nothing for egress.

Paths to actually zero, in order of leverage: partner with Hasadna, the Public Knowledge Workshop — they already run Israeli transit infrastructure as a nonprofit, already hold MOT access, and already pay for hosting, which answers the hosting question and the access question at once. Then sponsorship, where $50/month is a realistic ask for a daily-use transit app. Then credit programmes — AWS Activate and Open Data, Google Cloud, Microsoft for Startups, Cloudflare's open-source plans. Oracle's Always Free tier is worth an attempt but not a plan: it was cut from 4 OCPU/24 GB to 2 OCPU/12 GB in 2026 and Ampere capacity is frequently unavailable. Treat it as a lottery ticket.

Realtime is a pointer swap, not a query

Every 15–30 s the ingester parses a nationwide SIRI response into a brand-new immutable snapshot — trips by key, pre-sorted departure boards, vehicle positions — validates it against the previous one, and atomically replaces the reference. Readers take a local copy of the pointer and are done: no locks, no contention, no allocation. Staleness is a field on every response, so when the snapshot ages past 90 seconds the API stops claiming live data instead of serving confident nonsense.

Contributors have no MOT key

So the realtime source is an interface with two implementations: live SIRI, and replay from recorded snapshots. The repo ships a fixture bundle — a GTFS extract, TripIdToDate rows, a few hours of SIRI, a sample alerts package — and docker compose up runs the entire stack against it with a pinnable clock. Integration tests run on fixtures in CI; only a nightly job touches live MOT.

09

Never break the running graph

External transport data is assumed to be wrong sometimes: malformed feeds, duplicated trips, stale positions, impossible coordinates, unreachable APIs. The pipelines are built so bad input degrades the service instead of breaking it.

The backend keeps its own normalised realtime shape — tripId, vehicleId, delaySeconds, expectedArrival, location — so SIRI structures never leak through the application. Health is measured: GTFS age, feed lag, matched/unmatched trip percentage, routing p95, geocoding latency, API error rate.

11

The scope boundary

The non-goals are load-bearing. Everything on the right is a common reason transit apps get slow, cluttered and monetised — none of it ships without a clear transportation benefit.

In scope for V1

  • Buses, Israel Railways, light rail where data exists
  • Walking segments and transfers
  • Destination search in Hebrew and English
  • Three ranked journey alternatives
  • Journey timeline with stops and exits
  • Live arrivals and delays
  • Stop departure boards, favourite stops
  • Service alerts attached to journeys
  • Map with route, stops and transfer points
  • On-device favourites, no account

Explicitly not built

  • Fare payment and Rav-Kav management
  • Credit cards and loyalty programmes
  • Taxis, scooters, bikes, car and ride sharing
  • Advertising and promotions
  • Social feeds, chat, user posts
  • AI assistant
  • Complex account systems
  • Server-side location or commute history
  • Cloud sync in V1

Privacy default: location → route query → response → discard. No stored GPS trail, no commute history, no home or work address on a server, no identity. Live journey tracking stays on-device wherever practical.

12

When to stop on purpose

Any one of these turns Phase 0 from a build into a decision. Discovering one is a successful feasibility test, not a failure.

01

Nationwide GTFS cannot be sustainably consumed.

02

No practical routing engine correctly processes Israeli transport data.

03

No sustainable realtime source can be obtained.

04

Realtime cannot be matched to static trips reliably enough to be useful.

05

The required datasets cannot legally be used in an open-source application.

06

A fundamental dependency requires an unsustainable commercial service.

13

How success gets measured

Primary metric

Can the developer use OpenTransit every day without opening Moovit?

Not downloads. If the answer is yes, the core product works. Everything else — realtime coverage per journey, routing success rate, crash-free sessions, result latency, returning users, contributors, stars, issues closed — is a secondary metric that only becomes meaningful afterwards.

Because the app now arrives a phase later, Phase 1 gets its own single metric: is the API fast and truthful enough that a client would only have to render it? Concretely — journeys at p95 under 350 ms server-side, realtime snapshot lag under 45 s, and a SIRI↔GTFS match rate above 90 %. All three published on /v1/status rather than asserted in a document.
