One machine,
holding the country

The backend is not a database application and not a proxy in front of the Ministry of Transport. It holds Israel's timetable and its live vehicle feed in memory, rebuilds each on its own clock, and answers every question without leaving the box.

The idea everything follows from

Two paths, one direction of flow

Every component in the system belongs to exactly one of two sides, and data crosses between them in one direction only. The cold path is slow, scheduled and allowed to fail: it downloads feeds, validates them, builds routing graphs, polls the realtime feed, reconciles trips and archives history. The hot path is per-request and never allowed to block: it reads what the cold path has already finished building, and serializes an answer.

The hot path never asks the cold path for anything. There is no request-time fetch, no lazy load, and no cache miss that reaches the network.

RULE 1

Nothing on the hot path leaves the machine

Not Postgres, not object storage, not the Ministry, not another availability zone. A journey request touches memory and a process on loopback — nothing else.

RULE 2

Nothing on the hot path mutates shared state

New data arrives as a complete immutable object that atomically replaces the old one. Readers never lock, never coordinate, and never observe a half-updated world.

Almost every specific decision below is downstream of those two sentences. When a proposed change violates one of them, it is the change that is wrong.

The discipline is worth it because of where this product gets used: in a doorway, in the rain, with one thumb, deciding whether to run for a bus. The felt quality is almost entirely latency and honesty. Query-the-database-then-call-the-upstream puts a round trip and a cache-miss cliff in front of every one of those moments. Israel's transit network is small enough that the fast version is also the simple one.

The shape

What talks to what, and when

Read this as a statement about permission, not only topology. Everything on the cold side is reachable only on a schedule — never while a request is in flight.

What the system holds

Four data planes, four clocks

The planes are deliberately not merged. The schedule plane is large and slow; the realtime plane is small and fast. Keeping them apart is what lets the expensive one be rebuilt nightly while the cheap one is replaced every fifteen seconds. A journey response is the join of the first three, performed per request, in memory, in about a millisecond.

PlaneContentsRebuild clockLives inIf it goes stale
Schedule GTFS routes, trips, stops, calendars, shapes nightly MOTIS graph + stop index journeys are wrong by a timetable revision — serious, slow-moving
Realtime SIRI positions, predicted calls, delays 15–30 s immutable snapshot in RAM the API stops claiming live and says scheduled
Disruption GTFS-RT service alerts 5 min immutable alert set in RAM journeys lose warnings but stay correct
History archived SIRI observations, daily rollups append-only object storage + Postgres nothing user-visible — analytics only

The fourth plane exists only so Phase 4 has something to learn from, and it is architecturally inert: no user-facing request may ever read it. That single constraint is what makes a Postgres outage not an outage.

The parts

Defined by what they may not do

Describing a component by its prohibitions is more useful than describing it by its features, because the prohibitions are what the architecture is actually made of.

Transit.Api
Hot

The only public surface. Resolves places, calls MOTIS, overlays realtime and alerts, ranks, serializes. Holds hundreds of megabytes of transit state in RAM on purpose.

NeverOpens a database connection, calls the Ministry, or lets an upstream structure into a response body. No SIRI field name and no MOTIS type is part of the contract.

MOTIS
Hot

The routing engine, as a sidecar on loopback: timetable and street graph in RAM, RAPTOR queries in tens of milliseconds, probably geocoding and tiles from the same data.

NeverReached over a network hop. It is the only genuinely expensive step in a journey, so every millisecond of transport added to it lands on the product's slowest endpoint.

Transit.Ingest
Cold

One process, and the only holder of the Ministry key. Polls SIRI, polls alerts, builds the nightly graph, and owns SIRI ↔ GTFS reconciliation — once per snapshot, not once per request.

NeverDuplicated. MOT permits one poll per 15 seconds on a single key, and the key is a relationship with a government office rather than a credential that can be reissued at will.

Redis
Cold

Fan-out from the single ingester to any number of API instances, plus short-TTL shared cache.

NeverThe source of truth for anything. Total failure degrades the system to "each instance serves the last snapshot it received" — mild, bounded and self-healing.

Postgres + PostGIS
Cold

Static metadata, archived realtime, and the Phase 4 reliability statistics. Deliberately incomplete: the 60-day feed's stop_times runs to roughly a hundred million rows and is not loaded, because MOTIS already answers journeys and departures from RAM.

NeverOn the hot path, in any phase, for any endpoint.

Object storage
Cold

Everything durable and immutable, addressed by content hash: raw feeds exactly as MOT served them, normalized Parquet, built graphs, SIRI archives, contributor fixtures. A graph built from a given feed hash is buildable on a laptop and shippable to production unchanged.

NeverS3-specific. It is reached through IObjectStore, so R2, B2, Hetzner or a local MinIO substitute without a code change.

Inside a request

One step is the whole budget

A journey request, step by step. Realtime enrichment costs about a millisecond because it is a hash lookup into a structure that is already in memory — not a call to anything.

parse + validate1 ms
resolve from / to2 ms
MOTIS on loopback≤250 ms
overlay realtime1 ms
overlay alerts<1 ms
rank1 ms
serialize5 ms
Server time for GET /v1/journeys50–260 ms · p95 target 350 ms

That shape is the point of the design: performance work has exactly one target, and it is a component already optimized by other people for exactly this workload. The other two hot endpoints barely register — /v1/stops/{code}/departures is a single dictionary lookup into pre-sorted departure boards the snapshot already holds, and /v1/places answers roughly nine queries in ten from an in-process index of every Israeli stop and station, in Hebrew and English, before any geocoder is consulted.

The mechanism

Build it whole, prove it, then swap a pointer

One pattern, two clocks. Every fifteen to thirty seconds it produces a realtime snapshot; every night it produces a routing graph. In both cases the new thing is built completely and checked before anything points at it, so a reader never observes a partial state and a bad input can never take the service down.

Where it is allowed to change

Four interfaces carry the risk

These exist because each has a live chance of being swapped. Everywhere else, prefer concrete types — an interface with one implementation and no plausible second one is a cost, not a design.

IJourneyPlanner
MOTIS  →  OpenTripPlanner

The routing bake-off is still open. This is the largest single dependency in the system, so it is the one most deliberately wrapped.

IRealtimeSource
MotSiri  →  OpenBus  →  Replay

Ministry access is not yet granted. Which source wins is Phase 0's headline decision, and replay keeps development moving while it is made.

IGeocoder
MOTIS  →  Photon

Whether MOTIS handles Hebrew addressing well enough decides whether an Elasticsearch process and 2–4 GB of RAM exist at all.

IObjectStore
S3  →  R2 · B2 · MinIO

Provider independence is a stated principle of the project, and a principle is only real once it is compiled.

One module is not a seam and is not integration: Transit.Journeys holds the product's own logic. Ranking — lightly adjusted in Phase 1, realtime-aware in Phase 3, reliability-aware in Phase 4 — is where OpenTransit stops being a pleasant frontend for a routing engine. It lives in the backend because that is where the realtime state already is.

A data-model concern, not a UI one

Never make a guess look like a fact

Every transit leg carries scheduled, expected, delaySeconds and a realtime state. expected is never silently set equal to scheduled: when there is no live data, the state says so and the client renders it differently.

live stale scheduled unknown

Every snapshot carries its own recordedAt and coverage statistics. Once it ages past ninety seconds, the API stops claiming live data across the board rather than serving confident nonsense — and /v1/status is public, because a service people rely on to physically get somewhere should be honest about its own state.

The single most important number in the system is the reconciliation match rate: the share of SIRI observations successfully joined to GTFS trips. It is computed per snapshot, and it is the earliest possible warning that an upstream change has quietly broken the product. Below 90 % it warns; below 70 % it pages.

Degradation is a feature

Exactly one way to be down

Transport data is unreliable by nature: missing realtime, malformed feeds, duplicated trips, impossible coordinates, stale positions. The architecture assumes it, and loses capability in defined steps.

What breaksWhat the user seesSeverity
Realtime staleschedule times, every leg marked scheduled, state visible in /v1/statusdegraded
Alerts feed downjourneys without warnings, alerts: degradeddegraded
Geocoder downstops and stations still search from the in-process index; street addresses return a typed errordegraded
Redis downnothing — each instance serves its own last snapshotinvisible
Postgres downnothing at allinvisible
New GTFS invalidnothing — the previous graph keeps serving, the operator is pagedinvisible
MOT key revokedthe ladder above, plus an immediate page — this one needs a human, not a retrydegraded
MOTIS downa real outage — which is exactly why it sits on the same box with nothing between it and the APIoutage

One row in that table is a genuine outage. That is the design goal: collapse the number of ways the service can be down to one, and make every other failure a documented, visible reduction in what the API is willing to claim.

The whole thing, in one paragraph

The country's timetable and its live vehicle feed both live in RAM on one machine. A background process rebuilds them on their own clocks — nightly for the schedule, every fifteen seconds for realtime — and each rebuild finishes completely, and is proven, before it atomically replaces the old copy. Requests read those copies and nothing else. Everything durable is content-addressed in object storage, everything historical is off the request path entirely, and every dependency that might have to change sits behind an interface. Failures reduce what the API is willing to say, and say so out loud, rather than taking it down.
