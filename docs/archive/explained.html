01

What you are actually building

Before any of the architecture makes sense, it helps to be precise about what the thing is.

You are building a program that runs on a computer in a data centre, sits there waiting, and answers questions that arrive over the internet. Someone's phone asks "how do I get from Dizengoff Center to the Technion, leaving now?" and your program sends back a list of journeys. That program is the server. The phone app is the client.

Term
API

The exact list of questions your server will answer, and the exact shape of the answers. GET /v1/journeys?from=…&to=… is one question. An API is a contract: as long as the answers keep their shape, you can rewrite everything behind it and no client notices.

Your PRD makes an unusual call in §4.5: build the entire server first, finish it, and only then write the phone app. That is worth understanding, because it looks backwards — apps are the visible part.

The reasoning is that every client you will ever build (phone, web, a watch, someone's script) is a thin layer that draws whatever the server sends. If the server is slow, no amount of app polish hides it. If the server is fast and truthful, even a plain app feels excellent. So the interesting engineering is all on the server side, and building the app first would mean building the hard half twice.

02

The three kinds of data

Everything the product does comes from combining three separate streams of information. Almost every design decision downstream exists because these three behave so differently.

Term
GTFS — the plan

General Transit Feed Specification. A ZIP file full of plain text spreadsheets: stops.txt, routes.txt, trips.txt, stop_times.txt. It says bus 18 is scheduled to leave Arlozorov at 18:04. It is the timetable, and Israel's Ministry of Transport rewrites it nightly. It is a worldwide standard, so tools for reading it already exist.

Term
SIRI — the reality

Service Interface for Real Time Information. A live feed saying where vehicles actually are right now and when they are really expected. Bus 18 is running seven minutes late. It describes this moment only — there is no way to ask it about yesterday.

Term
Service alerts — the disruptions

A separate feed announcing that a stop is closed, or a route is diverted between 18:00 and 21:00. Delivered as protobuf, a compact binary format that needs decoding rather than being readable text like GTFS.

A journey answer is these three joined together: the plan says which buses exist, reality says how late they are, and disruptions say which parts you should not trust today.

The hard part nobody expects

The plan and the reality use different identity systems. SIRI says "I am journey 4471 on line 673." GTFS says "trip 18-2-A-y25." Nothing automatically connects them. Matching one to the other is called reconciliation, and your project has to do it itself — the Ministry documents the mapping, but the code is yours.

This is why your docs treat the match rate as the single most important number in the system. If matching quietly drops from 96 % to 40 %, nothing crashes — the app just silently stops knowing about delays, which is worse than crashing, because nobody notices.

03

Why speed is the whole problem

Your design targets look arbitrary until you see the numbers behind them. This section is the foundation for everything else — if you understand only one part of this page, make it this one.

Term
Latency, and p95

Latency is how long one request takes. p95 means: line up 100 requests slowest-last, and look at the 95th — 95 out of 100 were faster than this. Averages hide disasters. If 95 requests take 10 ms and 5 take 3 seconds, the average is a comfortable-sounding 160 ms, but one user in twenty waited three seconds. Percentiles catch that; averages don't.

Now the crucial fact. Different places a computer can fetch data from are not slightly different in speed. They are different by factors of thousands.

Getting data from…Real timeIf a memory lookup took 1 second
Memory (RAM), same program0.0001 ms1 second
Another program on the same machine~0.05 ms8 minutes
An SSD disk~0.1 ms17 minutes
A database on the same network~0.5–5 ms1.4–14 hours
A server in Frankfurt~50 ms6 days
Asking the Ministry's server~200 ms+3 weeks

Read the right-hand column again. Fetching from memory versus calling an external service is the difference between one second and three weeks. This is not an optimisation detail; it is the difference between a product that feels instant and one that feels broken.

The intuition

Memory is the notebook open on your desk. A database is walking to the filing room. An external API is posting a letter and waiting for the reply. Your design says: for anything a user is waiting on, only ever look at the notebook on the desk.

So when your documents insist that a journey request must never touch a database or call the Ministry, that is not architectural fussiness. Doing those things would blow the entire time budget on a single step.

04

The big idea: two paths

Here is the problem in one sentence: the data you need is slow to get, but the answers must be instant. Those two facts seem incompatible. The resolution is to stop doing the slow work while someone is waiting.

Split every piece of work in the system into one of two groups:

Cold pathHot path
When it runson a schedule — nightly, or every 15 secondswhile a person is waiting
Allowed to be slow?yes — it can take minutesno — milliseconds
Allowed to fail?yes — try again next cycleno
What it doesdownloads feeds, checks them, builds data structures, saves historyreads what the cold path already built, and replies

The cold path does all the slow, risky work in advance and leaves the result sitting in memory, already shaped for answering questions. The hot path just reads it. Nothing is computed while the user waits — it was computed minutes or seconds ago.

The rule everything follows from
No request that a person is waiting on may make a call that leaves the machine.

Not to a database, not to storage, not to the Ministry, not to another building. If a proposed change breaks this rule, the change is wrong. This one sentence generates almost every other decision in your design documents.

There is one deliberate exception: the routing engine, which does the genuinely hard computation. It runs as a separate program on the same physical machine, so talking to it never touches a network cable. That's the "8 minutes" row in the table above rather than the "6 days" one — affordable, where a real network call would not be.

05

The swap: updating data nobody is allowed to wait for

This is the cleverest part of the design and it is worth going slowly.

You have bus positions in memory. Every 15 seconds fresh ones arrive. Meanwhile, dozens of requests per second are reading that same data. How do you update information that is being read constantly?

The obvious answer, and why it's bad

The textbook approach is a lock: a "one at a time" rule. The updater locks the data, changes it, unlocks. Readers wait their turn.

This is correct but slow. Everyone queues. At fifty requests a second all wanting the same bus data, that queue becomes the bottleneck — and you have reintroduced waiting into the one place you spent the whole design removing it.

What your design does instead

Never modify the data at all. Instead:

Build a complete new copy off to the side, while everyone keeps reading the old one. Check the new copy is sane. Then change a single arrow — the one that says "the current data is over here" — to point at the new copy instead.

Term
Reference (or pointer)

A variable that holds where something is, rather than the thing itself. Like a signpost. Changing where a signpost points is one tiny, instant action — nothing can catch it half-done. Copying a whole building is not.

Because that arrow-change is a single indivisible step, every reader sees either the complete old data or the complete new data. Nobody can ever see a half-updated mixture. And because nothing is ever modified in place, no locks are needed at all. Readers never wait for anything.

The intuition

A departure board at a station. You could rub out and rewrite each line while passengers read it — they'd see nonsense mid-edit, and you'd have to shoo them away while you worked. Instead you print a whole fresh board in the back office, check it, then swap it into the frame in one motion. Nobody ever sees a half-written board, and nobody has to be shooed.

This pattern also gives you something valuable for free. If the new copy turns out to be broken — the Ministry published a corrupt file, half the stops are missing — you simply don't move the arrow. Everyone carries on using yesterday's perfectly good data, and you get an alert. A bad input can never take the service down.

06

The parts, in plain words

Your documents name about seven components. Here is what each one actually is, and the job it does.

Transit.Api
Hot
Your program. It receives the questions, looks things up in memory, asks the routing engine for journeys, and sends answers back. This is the part you write.
MOTIS
Hot
The routing engine — existing open-source software that solves the genuinely hard problem: given a timetable and a start and end point, find good journeys. This is much harder than finding a route on a road map, because a road is always there, whereas a bus exists only at 18:04. You don't write this; writing a good one is research-level work.
Transit.Ingest
Cold
A program with no users. It just wakes on a timer, downloads from the Ministry, and prepares data for the API. It is also the only part holding the Ministry access key — because the Ministry allows one request every 15 seconds, and running two copies risks losing access entirely.
Redis
Cold
A very fast shared noticeboard. Used here for one job: when the ingester builds fresh data, it posts it here so that every copy of your API picks it up. If you only ever run one copy of the API, you barely need this yet.
Postgres
Cold
A traditional database. Notice what it is not used for: answering user questions. It stores history for later analysis. This surprises most beginners, because the standard lesson is "put data in a database and query it" — but a database query means leaving your program and waiting, which the speed table in §03 rules out.
Object storage
Cold
Files kept somewhere durable — think Dropbox for programs. It holds the exact files the Ministry served, prepared routing data, and the archive of live observations. Crucially the Ministry overwrites its files and keeps no history, so anything you don't save yourself is gone forever.
The edge / Cloudflare
Hot
A service sitting in front of your server that handles encryption, blocks abuse, and keeps copies of common answers close to users. Mostly free, and it means your one machine isn't directly exposed to the whole internet.
07

Why the design hides things behind interfaces

Your documents keep mentioning names like IJourneyPlanner and IObjectStore. The I stands for interface.

Term
Interface

A promise about what something does, without saying how. "Give me a start, an end and a time; I'll give you journeys." Anything that keeps that promise can be plugged in, and the rest of your code cannot tell the difference.

Why bother? Because four decisions in your project are genuinely undecided, and each could be forced to change by something outside your control:

InterfaceThe question it keeps open
IJourneyPlannerMOTIS, or OpenTripPlanner if MOTIS handles Israeli data badly
IRealtimeSourcethe Ministry's feed, a volunteer service, or recorded data — you don't have the key yet
IGeocoderwhether you need extra software to turn Hebrew addresses into coordinates
IObjectStorewhich storage provider — so you can move to a cheaper one without rewriting

The important discipline is the opposite one: don't do this everywhere. An interface with only one possible implementation is extra work with no benefit. These four earn it because each has a real chance of changing.

08

When things break — and they will

Transit data is messy. Feeds go down, files arrive corrupted, vehicles report impossible positions, identifiers change without warning. A design that assumes everything works is a design that will be broken most mornings.

So instead of "working or broken," the system has degrees of working. Each failure removes one capability and the service keeps running:

If this breaks…The user gets…
Live bus data goes staletimetable times, clearly labelled as scheduled rather than live
Alerts feed goes downjourneys without disruption warnings
Redis goes downnothing — each API copy keeps using the data it already has
Postgres goes downnothing at all
A corrupt timetable arrivesnothing — yesterday's good data keeps serving
The routing engine diesa genuine outage — the only one on the list

One row is a real failure. That's the goal: reduce the number of ways to be truly down to one, and turn everything else into a visible, honest reduction in what the service claims to know.

The principle underneath
Never make a guess look like a fact.

Every time your API reports a bus, it also says whether that time is live, stale, scheduled or unknown. When the live feed is more than 90 seconds old, the system stops claiming to know and says so. Someone standing at a bus stop in the rain deserves to know the difference between "it's coming in 4 minutes" and "it was supposed to come in 4 minutes."

Every term from your documents, in one place.

Where to go next

You do not need to understand everything before starting. The build order in your documents is deliberately arranged so each step teaches you the next one.

  • Start with M1 — a server that answers a single trivial request. It teaches you the whole shape without any transit complexity.
  • Then M2 — download the Ministry's GTFS file and read it. Nothing clever, just proving you can get the data.
  • Then M3 — connect the routing engine, and get your first real journey out.
  • Realtime comes fifth, not first. It is the hardest part and it is blocked on the Ministry answering an email — so it is deliberately not where you begin.

Re-read docs/architecture.md after M3. Much of it will have stopped being abstract by then, because you will have built the parts it describes.
