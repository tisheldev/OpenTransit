# OpenTransit Israel — Phase 0 Vertical-Slice MVP Plan

**Status:** Proposed execution plan  
**Purpose:** Build a production-shaped, high-performance transit backend through usable vertical slices instead of a backend-first waterfall  
**Target:** A fast, expandable API demonstrated by a deliberately minimal mobile-first client using real Israeli transit data  
**Portfolio thesis:** Full-country routing and realtime enrichment can be made predictably fast on modest hardware, with evidence that others can reproduce  
**Planning horizon:** Approximately 28–34 focused developer-days, plus any waiting time for MOT access  
**Cost ceiling:** $0 locally; no more than $25/month during Phase 0 without an explicit decision

---

## 1. Phase 0 outcome

Phase 0 ends with a small application that can be installed or opened on a phone and used to plan real journeys in Israel. The client proves the backend in a real product flow; the backend, its performance evidence, and its operational behavior are the main engineering deliverables.

A user can:

1. Open a mobile-first web client.
2. Search for an origin and destination in Hebrew or English.
3. Request a journey for now or a selected time.
4. See approximately three schedule-based alternatives with walking and transfers.
5. Open a readable journey timeline.
6. See realtime information when it is trustworthy.
7. See a clear scheduled/stale/unknown state when realtime is missing.
8. See relevant service alerts if access to the alert feed is available.

The application is not expected to be visually polished, highly available, or ready for an app store. It must be real enough to dogfood, small enough to finish, and instrumented well enough to prove where its speed comes from.

The primary Phase 0 question is:

> Can one person use this vertical slice for ordinary Israeli journeys, experience a meaningfully fast result, and see a credible path from this backend to the larger product?

Phase 0 must leave behind five durable assets:

1. An expandable modular backend, not a throwaway POC.
2. A minimal client that proves perceived speed and API usefulness.
3. Reproducible full-feed benchmarks with hardware, configuration, feed hash, and commit provenance.
4. Evidence-backed architecture decisions explaining which optimizations mattered.
5. Honest capacity and cost limits instead of projected user-count claims.

## 2. Principles for this phase

### 2.1 Every milestone crosses the whole stack

No milestone ends with only a library, schema, ingestion service, or architecture document. Each milestone must improve something visible in the client.

The client improvement may be small. Its role is to exercise the real request path, expose contract mistakes, and demonstrate perceived speed—not to compete with the backend for Phase 0 effort.

The slices are:

```text
Slice 1  coordinates → thin API → MOTIS → journey shown in browser
Slice 2  place search → journey alternatives → journey detail
Slice 3  realtime sample → journey truth state → visible client badge
Slice 4  live deployment → phone dogfooding → measured findings
```

### 2.2 The API is deliberately unstable

Phase 0 uses `/v0`. Breaking changes are expected while the client reveals what the contract needs. A stable public `/v1` is a later result, not an input.

### 2.3 Architecture follows measurements

Phase 0 records actual:

- MOTIS import time
- Peak and steady memory
- Disk usage
- Journey latency
- Search quality
- Route correctness
- SIRI-to-GTFS match rate by operator and mode
- Requests generated by a real client session

Redis, Postgres, Photon, multi-instance deployment, custom ranking, and historical analytics remain absent until a measurement creates a need for them.

Performance engineering is not deferred with that infrastructure. Request budgets, bounded concurrency, immutable read state, profiling, and repeatable load tests are part of the baseline because speed is the product and the portfolio thesis.

### 2.4 Reuse the routing engine before extending it

MOTIS should own routing, walking, scheduled departures, and—if the realtime experiment succeeds—realtime-aware routing. The thin API normalizes and constrains MOTIS; it does not reimplement it.

### 2.5 Product truth is more important than feature count

The client must distinguish:

- `live`
- `partial`
- `scheduled`
- `stale`
- `unknown`

It must never label an itinerary live merely because one of several legs has realtime data.

### 2.6 Speed is a measured product feature

Every backend milestone reports:

- p50, p95, and p99 latency
- Throughput at increasing concurrency
- Error and timeout rate
- API time separated from MOTIS time
- Peak and steady memory
- Cold and warm behavior
- The first saturated resource
- Regression or improvement relative to the previous milestone

The project does not claim capacity in users. It reports the tested request mix, concurrency, hardware, and point at which latency or errors become unacceptable.

### 2.7 Overengineer the hot path, underengineer the platform

Phase 0 deliberately invests in:

- No unstable third-party call during a user request
- Strictly bounded routing inputs and concurrency
- Precomputed realtime reconciliation
- Immutable, versioned read state
- Last-known-good feed activation
- A normalized domain model independent of MOTIS and SIRI wire structures
- Request cancellation and timeouts

Phase 0 does not invest in multi-node infrastructure, generalized storage platforms, or operational components that have no current consumer.

## 3. Scope

### 3.1 Required for the Phase 0 MVP

- Minimal mobile-first responsive web client/PWA with three screens: search, alternatives, and journey timeline
- Hebrew and English interface direction and text handling
- Origin and destination search
- Current location as an optional origin
- Depart-now and selected departure time
- Walking, bus, rail, and light rail when present in the feed
- Journey alternatives
- Journey detail timeline
- Scheduled versus realtime state
- Basic service alert presentation if the real feed is available
- Feed and API health visible to the client
- One-command local development using fixtures or public static data
- One small deployment for phone dogfooding if legal/data-access conditions permit
- Reproducible load-test scenarios using the full intended Israeli dataset
- Profiling for CPU, allocation/GC, snapshot construction, and slow journey cases
- Bounded routing concurrency, input limits, request cancellation, and timeouts
- Backend metrics separating API work, MOTIS work, and realtime-enrichment work
- Versioned benchmark reports suitable for a public portfolio

### 3.2 Explicitly deferred

- Native iOS or Android applications
- App-store distribution
- User accounts and cloud sync
- Payments and Rav-Kav features
- Favourite places beyond optional local browser storage
- Live turn-by-turn journey mode
- Background GPS and notifications
- Full vehicle map
- Historical reliability scoring
- Custom journey ranking
- Public stable API guarantees
- Generated client SDKs
- Multi-instance high availability
- Redis
- Postgres/PostGIS
- Elasticsearch/Photon unless the search experiment proves MOTIS inadequate
- A custom nationwide stop index unless the search experiment proves it necessary
- Kubernetes, managed databases, load balancers, or multi-region deployment
- Broad user research, visual-design exploration, animation, and nonessential client polish
- UI work that cannot be tied to journey comprehension or perceived speed

### 3.3 Stretch items

Stretch work may begin only after the required exit criteria are green:

- Simple route map on the journey-detail screen
- Local recent searches
- Favourite stops
- Stop departure board
- Shareable journey link
- Installable PWA shell and offline error screen

### 3.4 Phase 0 effort allocation

The intended effort split is:

| Area | Target share |
| --- | ---: |
| Backend, ingestion, realtime, and performance engineering | 70–80% |
| Minimal client and end-to-end integration | 10–20% |
| Deployment, evidence, and documentation | approximately 10% |

If client polish starts displacing performance or data work, stop at the smallest UI that can demonstrate and dogfood the current backend slice.

## 4. Thin target architecture

```text
MOBILE WEB CLIENT / PWA
  search · results · timeline · realtime truth state
                    |
                    | HTTPS /v0
                    v
THIN API
  input validation · privacy · response normalization · strict limits
                    |
                    | loopback HTTP
                    v
MOTIS
  geocoding · walking · timetable · routing · realtime if adapter succeeds
                    ^
                    |
BACKGROUND UPDATE COMMANDS
  GTFS download/validation · MOTIS import · SIRI adapter · alert adapter
                    |
           local versioned files
      optional object storage only when deployed
```

Phase 0 should normally run as three processes:

1. Client development server or static web files.
2. Thin API.
3. MOTIS.

Feed updates and adapters are commands or scheduled jobs, not permanent platforms. A separate ingester process is introduced only if the MOT credential or polling cadence requires it.

The source should be a modular monolith around the MOTIS process:

```text
OpenTransit
├── api
│   ├── places
│   ├── journeys
│   ├── departures
│   └── health
├── domain
│   ├── places
│   ├── journeys
│   ├── realtime
│   └── alerts
├── adapters
│   ├── motis
│   ├── mot-siri
│   ├── replay-realtime
│   └── gtfs
├── ingestion
│   ├── static-feed
│   ├── reconciliation
│   └── snapshots
├── performance
│   ├── scenarios
│   ├── load-tests
│   └── reports
└── web
    └── minimal-client
```

Use interfaces only at dependencies with a credible Phase 0 reason to change:

- `JourneyPlanner`
- `PlaceSearcher`
- `RealtimeSource`
- `AlertSource`
- `Clock`

Prefer concrete types everywhere else. Expandability comes from a stable internal domain model and narrow dependency seams, not an interface for every class.

### 4.1 Default technology decision

Use the developer's fastest well-supported stack. If there is no strong preference, the default recommendation is:

- TypeScript for the client and thin API
- React + Vite for the mobile-first PWA
- Fastify for the API
- MOTIS as the routing/geocoding process
- Vitest and Playwright for automated tests
- Docker Compose only for MOTIS and integration-level local startup

This default keeps the client and API in one language while MOTIS owns the computational work. It is a recommendation, not a product requirement. The choice must be recorded once before Task F0.3 and not revisited during Phase 0 unless a concrete blocker appears.

### 4.2 Minimal API surface

```text
GET  /v0/health
GET  /v0/places?q=&lang=&near=
POST /v0/journeys
GET  /v0/stops/{id}/departures       stretch until the core journey works
```

Use `POST /v0/journeys` so exact origin/destination coordinates do not appear in URLs, browser history, or normal proxy access logs.

Minimum request:

```json
{
  "from": { "type": "coordinate", "lat": 32.075, "lon": 34.775 },
  "to": { "type": "place", "id": "..." },
  "departAt": "2026-08-29T17:40:00+03:00",
  "locale": "he"
}
```

Minimum response concepts:

```text
Journey
  id                  opaque for the lifetime of this response only
  startTime
  endTime
  durationSeconds
  walkingSeconds
  transferCount
  realtimeState
  legs[]

Leg
  type                walk | transit
  startTime
  endTime
  geometry            optional in the first slice
  from / to
  route                transit only
  headsign             transit only
  scheduledTimes
  expectedTimes        nullable
  realtimeState        live | scheduled | stale | unknown
```

The API returns only the fields used by the current client plus identifiers needed for debugging. It does not attempt to anticipate watch, public-SDK, analytics, or third-party-client requirements.

### 4.3 Initial performance budgets

These are design budgets for the first target host, not claims of achieved performance. Task B0.1 defines the exact measurement method and Task B1.1 establishes the first baseline.

| Operation | Initial Phase 0 budget |
| --- | ---: |
| `GET /v0/places` | p95 under 50 ms |
| `POST /v0/journeys` | p95 under 400 ms |
| `GET /v0/stops/{id}/departures` | p95 under 50 ms when implemented |
| API realtime-enrichment overhead | p95 under 5 ms |
| Errors/timeouts under the supported load mix | under 0.5% |
| Client search selection to useful alternatives | under 1 second on the measured test connection when practical |

If the first full-data measurement misses a budget, do not quietly loosen it. Record whether the budget, architecture, host, or implementation should change.

### 4.4 Benchmark provenance

Every published result must include:

- Git commit
- GTFS and `TripIdToDate` hashes
- OSM input and date
- MOTIS version and configuration
- API build/runtime version
- Host CPU, memory, operating system, and architecture
- Cold/warm state
- Request scenario and concurrency
- Sample count and test duration
- p50/p95/p99, throughput, errors, CPU, and memory

A benchmark without this context is a development hint, not portfolio evidence.

## 5. Workstreams

The work is organized into seven streams. Streams may overlap, but product slices—not component completion—control the milestones.

| Stream | Purpose |
| --- | --- |
| F | Foundation, success criteria, fixtures, and decisions |
| D | Static data and MOTIS routing |
| P | Product client and thin API |
| R | Realtime and service-alert access/integration |
| B | Benchmarks, profiling, capacity, and performance regression |
| O | Deployment, security, privacy, and operations |
| V | Validation, dogfooding, and Phase 0 decision |

Estimates below are focused developer time, not calendar promises. Waiting for MOT is tracked separately and must not block the static vertical slice.

## 6. Milestone 0 — Define the evidence and unblock access

**Target:** Day 1  
**Visible result:** A placeholder client can call a placeholder `/v0/health`, and all Phase 0 uncertainties have owners and tests.

### F0.1 — Freeze Phase 0 scope

**Estimate:** 0.25 day  
**Dependencies:** none

Tasks:

- Copy the required/deferred lists in this document into the project tracker.
- Mark every deferred feature as not eligible for Phase 0 implementation.
- Set the Phase 0 infrastructure ceiling to $25/month.
- Name one decision owner; for a solo project this is the developer.

Acceptance:

- Every new Phase 0 issue maps to a required outcome or is rejected/deferred.
- No issue is justified only by a hypothetical future client.

### F0.2 — Build benchmark corpora before building features

**Estimate:** 0.75 day  
**Dependencies:** F0.1

Create versioned test data containing:

- 25 representative journey cases
- 100 representative place queries
- 10 known stops with expected upcoming services
- Known edge cases for after-midnight service, holiday/service-day behavior, no-route, and long-distance travel

Journey mix:

| Category | Minimum cases |
| --- | ---: |
| Tel Aviv urban bus | 4 |
| Jerusalem urban/light rail | 3 |
| Haifa urban | 3 |
| Intercity rail | 4 |
| Bus → rail and rail → bus | 4 |
| At least one transfer | 2 |
| Late night/service-day boundary | 2 |
| No reasonable route | 1 |
| Accessibility or unusually long walk edge case | 1 |
| Holiday/weekend schedule case | 1 |

Place-query mix:

- Hebrew and English
- Addresses
- Stations and stops
- Universities, hospitals, malls, and landmarks
- Neighborhoods
- Common misspellings
- Multiple English transliterations of the same Hebrew name
- Queries whose correct result depends on `near`

Acceptance:

- Inputs and expected qualitative outcomes are committed as data, not prose alone.
- Commercial route planners may be recorded as comparison evidence, never as automatic ground truth.

### F0.3 — Choose one Phase 0 implementation stack

**Estimate:** 0.25 day  
**Dependencies:** F0.1

Decision criteria, in order:

1. Developer delivery speed.
2. Ability to call and normalize MOTIS.
3. Test tooling.
4. Low memory/operational overhead.
5. Future performance only after the above.

Acceptance:

- One short ADR records the choice and rejected alternative.
- No second backend language is added in Phase 0.

### B0.1 — Establish the performance methodology and harness

**Estimate:** 1 day  
**Dependencies:** F0.2, F0.3

Create a repeatable performance command that can evolve with the API. It must support:

- A fixed request corpus rather than one convenient route
- Cold and warm runs
- Configurable concurrency and duration
- Per-endpoint and combined workload runs
- p50, p95, p99, throughput, errors, and timeouts
- Host CPU and memory capture
- Separate API and MOTIS timing from response trace data
- Machine-readable results plus a short Markdown summary

The eventual representative workload starts with this mix and is revised from dogfood evidence:

```text
45% place search
35% journey planning
10% departures
 5% journey/trip detail when implemented
 5% health/status
```

Early milestones run only the endpoints that exist and renormalize the mix. Journey tests must cover short urban, multimodal, intercity, late-night, and no-route cases.

Acceptance:

- One command produces a timestamped result tied to a commit and environment description.
- A placeholder or fixture-backed endpoint can be tested before MOTIS integration.
- The result format can compare two runs without copying numbers manually.
- The methodology states that performance tests run against optimized/release builds, not development hot-reload servers.

### R0.1 — Send the MOT request

**Estimate:** 0.25 day  
**Dependencies:** none  
**Calendar-critical:** yes

Request in one message:

- SIRI-SM 2.8 access
- Service Alerts feed access
- Whether access is tied to an IP, geography, organization, or application
- Polling and concurrent-client restrictions
- Permission to operate a public open-source application
- Permission to store normalized observations
- Permission to publish recorded fixtures
- Permission or restrictions on redistributing derived realtime data

Acceptance:

- Request sent and date recorded.
- Follow-up dates are scheduled for one and three weeks.
- A four-week decision date is recorded, but it does not stop static MVP work.

### P0.1 — Walking skeleton

**Estimate:** 0.75 day  
**Dependencies:** F0.3

Tasks:

- Create client and API packages.
- Add `/v0/health`.
- Render API state in a mobile-width client page.
- Add lint, unit test, and one browser smoke test.
- Add a single local startup command.

Acceptance:

- A browser at mobile width shows `API ready` based on a real HTTP call.
- A failing API produces a visible degraded/error state, not an empty screen.

### Milestone 0 exit

- [ ] Scope frozen
- [ ] Benchmark corpora exist
- [ ] Technology choice recorded
- [ ] Reproducible performance harness produces a versioned report
- [ ] MOT request sent
- [ ] Client-to-API skeleton works

## 7. Milestone 1 — First static vertical slice

**Target:** Focused days 2–8  
**Visible result:** Enter two coordinates in the client and see a real Israeli multimodal journey.

### D1.1 — Acquire and version static inputs

**Estimate:** 0.5 day  
**Dependencies:** F0.3

Tasks:

- Download `Gtfs_10_days.zip` and `TripIdToDate.zip` with `GET`.
- Download the selected Israel OSM extract.
- Record URL, retrieval time, byte size, and SHA-256 for each input.
- Validate zip integrity and required GTFS files.
- Store inputs under a local version directory.
- Do not introduce S3 or a database.

Acceptance:

- Re-running the command is idempotent.
- A corrupt or partial download is rejected.
- The exact source combination used by an import is reproducible.

### D1.2 — Import full Israel into MOTIS and measure it

**Estimate:** 1 day  
**Dependencies:** D1.1

Measure separately:

- Import elapsed time
- Peak resident memory
- Steady server memory
- Disk usage by artifact type
- Startup time
- Basic geocoder readiness
- Five warm and five cold route queries

Test at least two configurations if practical:

1. Routing + walking + geocoding, without tiles.
2. Minimal routing configuration without optional features.

Acceptance:

- MOTIS starts from the full intended feed, not a city extract.
- At least 20 of the 25 benchmark journey requests return structurally valid results.
- Actual resource measurements replace estimates in the decision log.
- If the target development machine cannot complete the import, record the precise bottleneck before considering OTP or larger hosting.

### D1.3 — Validate route semantics

**Estimate:** 1 day  
**Dependencies:** D1.2, F0.2

For each benchmark journey, record:

- Result found or not found
- Modes
- Walking time
- Transfers
- Departure and arrival time
- Suspicious transfer or impossible walking segment
- Service-day correctness
- Qualitative comparison with one or more reference planners

Acceptance:

- At least 23 of 25 cases are reasonable, or every failure has a bounded explanation and next experiment.
- No accepted journey uses the wrong service day or an obviously impossible transfer.
- A result is not marked correct merely because another planner produced something similar.

### P1.1 — Implement minimal journey API

**Estimate:** 1 day  
**Dependencies:** D1.2

Tasks:

- Implement `POST /v0/journeys` for coordinate origins/destinations.
- Validate coordinate bounds, timestamp, locale, result count, and walking limits.
- Set strict MOTIS timeouts and maximum results.
- Normalize only fields required by the first result card and timeline.
- Preserve upstream identifiers in a debug-only section when development mode is enabled.
- Return typed `NO_ROUTE`, `INVALID_REQUEST`, `ROUTER_UNAVAILABLE`, and `OUTSIDE_COVERAGE` errors.

Acceptance:

- The API passes at least 20 benchmark cases.
- User input cannot request unbounded results, walking time, or search windows.
- All journeys are explicitly marked `scheduled` in this milestone.

### P1.2 — Implement coordinate journey client

**Estimate:** 1.5 days  
**Dependencies:** P1.1

Client states:

- Empty form
- Loading
- Results
- No route
- Validation error
- Router unavailable

UI:

- Origin and destination coordinate fields, temporarily
- Depart now or selected time
- Three result cards at most
- Journey detail timeline
- Walking/transit leg distinction
- RTL layout when Hebrew is selected

Acceptance:

- A phone-sized browser can request and inspect a real journey without developer tools.
- Back navigation from detail to results preserves the results.
- Loading and failure are understandable.
- Basic keyboard navigation and readable semantic headings work.

### P1.3 — Add contract and browser integration tests

**Estimate:** 0.75 day  
**Dependencies:** P1.1, P1.2

Acceptance:

- One test starts from the client, requests a fixture-backed journey, opens the result, and verifies the leg timeline.
- API tests validate bounds and typed errors.
- Tests do not require a live MOT endpoint.

### B1.1 — Establish the full-data static-routing baseline

**Estimate:** 1.5 days  
**Dependencies:** D1.3, P1.1, B0.1

Run optimized builds against the full intended data and:

- Measure cold and warm latency for the journey corpus.
- Increase concurrency through at least `1, 2, 4, 8, 16` until a resource or latency budget saturates.
- Record queueing, throughput, errors, timeouts, CPU, and memory.
- Separate API validation/normalization/serialization time from MOTIS time.
- Verify request cancellation reaches the MOTIS adapter or otherwise releases API capacity promptly.
- Profile the slowest representative and p99 scenarios.
- Record allocations/GC behavior for the API process.
- Identify whether the first bottleneck is CPU, MOTIS concurrency, API allocation, memory, disk, or an artificial limit.

Acceptance:

- The first public-style performance report is reproducible from the repository.
- Results state the maximum tested supported load on the measured machine; they do not convert it into an unsupported daily-user claim.
- Any miss against the initial 400 ms p95 journey budget has a profile-backed explanation or a time-boxed next experiment.
- A deliberately expensive request is rejected or times out without destabilizing subsequent normal requests.

### Milestone 1 exit

- [ ] Full Israeli static data routes successfully
- [ ] Memory, disk, import time, and latency are measured
- [ ] Coordinate-to-journey works end to end in a mobile browser
- [ ] Route-quality failures are recorded, not hidden
- [ ] Full-data p50/p95/p99, saturation point, and first bottleneck are recorded

This is the first usable increment. It should be demonstrated before place-search implementation begins.

## 8. Milestone 2 — Searchable static MVP

**Target:** Focused days 9–14  
**Visible result:** Search for real places and plan a journey without coordinates.

### D2.1 — Benchmark MOTIS geocoding

**Estimate:** 1 day  
**Dependencies:** D1.2, F0.2

For all 100 place queries, capture:

- Correct result rank
- Result type
- Language/label quality
- Coordinate correctness
- Whether `near` improves ranking
- Latency
- Failure reason

Suggested initial thresholds for a go/no-go conversation, not permanent product SLOs:

- Desired result in top 3 for at least 85% of the corpus
- Desired result first for at least 70%
- No systematic failure across an entire required category such as Hebrew addresses

Acceptance:

- Search quality is summarized by category, not one global number alone.
- A decision is made among:
  - MOTIS alone
  - MOTIS plus a very small curated alias/POI overlay
  - A time-boxed alternative-geocoder spike
- Photon is not deployed solely because several hand-picked queries failed.

### P2.1 — Implement `/v0/places`

**Estimate:** 1 day  
**Dependencies:** D2.1

Tasks:

- Normalize MOTIS place results into `id`, `label`, `secondaryLabel`, `type`, `lat`, and `lon`.
- Accept locale and optional proximity.
- Enforce minimum query length and maximum result count.
- Apply only measured normalization/aliases.
- Avoid logging raw query text by default.

Acceptance:

- The endpoint passes the chosen search-corpus threshold.
- Results have stable meaning within one active dataset version.
- Dataset changes may invalidate IDs during Phase 0; this behavior is documented rather than prematurely solved.

### P2.2 — Replace coordinate fields with search

**Estimate:** 1.5 days  
**Dependencies:** P2.1, P1.2

Tasks:

- Origin and destination autocomplete
- Current-location origin with an explicit permission action
- Debounced requests with cancellation of stale responses
- Search result types and secondary labels
- Clear origin/destination swap action
- Recent selection kept only in client memory initially

Acceptance:

- Slow earlier searches cannot overwrite newer results.
- Denied location permission has a clear fallback.
- Hebrew and English searches work with correct text direction.
- Selecting places and planning a journey requires no coordinate entry.

### P2.3 — Improve result and detail usefulness

**Estimate:** 1 day  
**Dependencies:** P2.2

Each result shows:

- Departure and arrival
- Total duration
- Walking duration
- Number of transfers
- Line names and modes
- Scheduled badge

The detail screen shows:

- Where to walk
- Boarding stop
- Line and headsign/direction
- Scheduled departure
- Exit stop
- Transfer walking segments
- Final arrival

Acceptance:

- A user unfamiliar with the raw GTFS data can explain where to board and exit.
- The client does not need to interpret MOTIS-specific types.
- No map is required to pass this milestone.

### B2.1 — Measure search and perceived result speed

**Estimate:** 1 day  
**Dependencies:** P2.3, B0.1

Backend work:

- Run the 100-query corpus through warm and cold search tests.
- Measure p50/p95/p99 and allocation behavior.
- Separate MOTIS geocoder time from API normalization and serialization.
- Test concurrent search while route planning is under load.
- Verify autocomplete cancellation prevents stale work from consuming capacity unnecessarily.

Client work is intentionally limited to measurement:

- Record selection-to-useful-results time on a phone-sized browser.
- Record API time, network time, and render time separately where possible.
- Conduct a structured self-test using ten journeys not used while designing the UI.
- Record only comprehension failures that imply an API-contract or essential presentation problem.

Acceptance:

- Search performance is reported together with relevance; a fast wrong result does not pass.
- The API is measured against the initial 50 ms p95 search budget.
- Route-planning load does not make autocomplete unusable without that contention being understood and documented.
- Contract changes discovered through the client are made in `/v0` immediately.

### Milestone 2 exit

- [ ] A real place-to-place journey can be planned on a phone
- [ ] Search quality is measured across a fixed corpus
- [ ] Results and detail are understandable without raw transit knowledge
- [ ] The API contract has been revised based on actual client use
- [ ] Backend and end-to-end perceived-speed results are recorded separately

This is the fallback MVP if realtime access ultimately fails.

## 9. Milestone 3 — Realtime decision and integration

**Target:** Focused days 15–23; may overlap Milestones 1–2  
**Visible result:** The same journey UI accurately shows live, partial, stale, or scheduled state.

This milestone is an experiment first. It must not start with the assumption that a custom API-side overlay is the correct architecture.

### R3.1 — Obtain lawful realtime samples

**Estimate:** 0.5 day  
**Dependencies:** R0.1 for direct MOT; otherwise public Open Bus source and terms review

Preferred source order:

1. Direct MOT sample supplied under acceptable terms.
2. Publicly archived Open Bus raw SIRI sample under acceptable terms.
3. A synthetic fixture for structural work only.

Acceptance:

- Source, retrieval time, licence/terms status, and allowed use are recorded.
- Synthetic data is never used to claim a real match rate.

### R3.2 — Parse and inventory SIRI-SM

**Estimate:** 1 day  
**Dependencies:** R3.1

Capture:

- Total active journeys
- Vehicles with positions
- Journeys with onward calls
- Missing identifiers by field
- Operators/modes represented
- Feed timestamp and observed delivery lag
- Raw and compressed payload sizes

Acceptance:

- A sample can be replayed deterministically.
- Parsing failures preserve the input and produce actionable diagnostics.

### R3.3 — Implement and measure reconciliation

**Estimate:** 2 days  
**Dependencies:** R3.2, D1.1

Matching stages:

1. Official `TripIdToDate` mapping.
2. Exact route/operator/direction/start-time evidence.
3. Conservative fallback only when the match is unambiguous.

Output classifications:

- `matched_exact`
- `matched_fallback`
- `ambiguous`
- `unmatched_missing_data`
- `unmatched_no_candidate`

Measure by:

- Operator
- Mode
- Hour of day
- Exact versus fallback match

Acceptance:

- No ambiguous trip is presented as a confident match.
- Match results are broken down by operator/mode; a national average cannot hide a broken operator.
- At least three different sample windows are tested.
- The acceptable threshold is decided from the product's target journeys, not selected solely to make the test pass.

### R3.4 — Realtime architecture bake-off

**Estimate:** 2 days, strictly time-boxed  
**Dependencies:** R3.3

Test in this order:

#### Option A — Adapt to GTFS-RT and let MOTIS route with realtime

- Convert matched SIRI observations into GTFS-RT TripUpdates and VehiclePositions.
- Feed them into MOTIS using a supported local mechanism.
- Test delays, cancellations if represented, and changed transfer feasibility.

#### Option B — Annotation-only API overlay

- Keep MOTIS schedule routing.
- Attach realtime state to matched legs after routing.
- Mark the entire journey `partial` or `scheduled` when appropriate.

Decision criteria:

| Criterion | Weight |
| --- | ---: |
| Correct handling of delayed/missed transfers | High |
| Cancellation and skipped-stop handling | High |
| Match transparency | High |
| Implementation and operational simplicity | High |
| Latency | Medium |
| Ability to replay fixtures | Medium |
| Future portability to OTP or another source | Low during Phase 0 |

Acceptance:

- One ADR records measured behavior for both attempted options.
- Option A is preferred if it works reliably because it avoids duplicating routing logic.
- Option B may be selected as a temporary Phase 0 fallback, but the UI must not imply realtime-aware routing.

### R3.5 — Define realtime truth semantics

**Estimate:** 0.5 day  
**Dependencies:** R3.4

Suggested journey-level rules:

| State | Meaning |
| --- | --- |
| `live` | Every transit leg that should have realtime coverage is confidently matched and fresh |
| `partial` | At least one relevant leg is live and at least one is scheduled/unknown |
| `scheduled` | No live data is claimed; timetable data is current |
| `stale` | Realtime was available but the source or observation exceeded its freshness limit |
| `unknown` | The system cannot establish a safe state |

Freshness should consider the individual observation and source timestamp, not only the age of the latest nationwide payload.

Acceptance:

- Unit tests cover mixed-leg journeys and stale observations.
- The API never silently copies scheduled times into expected-time fields.

### P3.1 — Render realtime in the existing client

**Estimate:** 1 day  
**Dependencies:** R3.5, P2.3

Tasks:

- Journey-level truth badge
- Leg-level scheduled and expected times
- Human-readable delay
- Partial-coverage explanation
- Stale-data warning
- No-data fallback

Acceptance:

- Removing the realtime source does not break journey planning.
- A partial journey cannot be mistaken for a fully live journey.
- The client uses normalized API states and contains no SIRI-specific logic.

### B3.1 — Measure realtime cost and concurrency behavior

**Estimate:** 1 day  
**Dependencies:** R3.4, R3.5, B1.1

Measure separately:

- SIRI parse time
- Reconciliation time by exact and fallback stage
- GTFS-RT conversion time if Option A is selected
- Snapshot construction time and peak allocation if Option B is selected
- Peak memory while old and new realtime state coexist
- API enrichment overhead per journey
- Read latency while a new realtime version is activated
- Behavior when malformed, unexpectedly large, or stale input arrives

Run the representative mixed workload with realtime enabled and compare it directly with the static baseline.

Acceptance:

- API-side realtime enrichment, if used, meets or has a profile-backed plan toward the initial 5 ms p95 overhead budget.
- Snapshot activation does not produce torn state, unbounded queueing, or a visible latency spike.
- Malformed realtime is rejected while the last valid state continues serving.
- The report shows the incremental CPU, memory, and latency cost of realtime rather than only total endpoint latency.

### R3.6 — Service-alert spike

**Estimate:** 1 day when data is available  
**Dependencies:** MOT alert access or a legally usable sample

Tasks:

- Decode the feed.
- Resolve alerts to route, stop, or trip identifiers.
- Attach applicable alerts to returned journeys.
- Show a short alert summary and original effective period.

Acceptance:

- At least one real/recent alert is attached correctly.
- If access is unavailable, fixture rendering is tested and live alerts remain explicitly disabled.
- Lack of alert access does not pretend that journeys are unaffected by disruptions.

### Milestone 3 exit

- [ ] Real matching quality is measured by operator/mode
- [ ] MOTIS realtime integration has been tested before choosing a custom overlay
- [ ] Realtime truth semantics are visible in the client
- [ ] Schedule-only degradation works
- [ ] Alert status is explicit: live, fixture-only, or unavailable
- [ ] Realtime parse, reconciliation, activation, and request overhead are measured

## 10. Milestone 4 — Deploy and dogfood

**Target:** Focused days 24–30 plus at least five calendar days of use  
**Visible result:** The developer uses the application from a phone against a deployed environment.

### O4.1 — Select hosting from measurements

**Estimate:** 0.5 day  
**Dependencies:** D1.2, R0.1 response if available

Decision inputs:

- Measured steady and peak memory
- Whether import/build happens on the serving host
- Whether MOT requires an Israeli/static IP
- Measured CPU under the benchmark mix
- Phase 0 $25/month ceiling

Rules:

- Do not choose an 8 GB host because the old design says 8 GB.
- Do not deploy Postgres, Redis, or Photon on the host unless a completed experiment requires them.
- Use local versioned disk first.
- Add inexpensive object storage only for artifacts that would be costly or impossible to recreate.

Acceptance:

- The selected host has at least 25% steady-state memory headroom after the whole required stack is running.
- Hosting decision and actual monthly price are recorded.
- If no host fits the ceiling, Phase 0 stays local and records the cost finding honestly.

### O4.2 — Minimal secure deployment

**Estimate:** 1.5 days  
**Dependencies:** O4.1

Tasks:

- TLS termination
- Non-root containers/processes where practical
- Secrets outside source control
- Firewall exposing only required ports
- API request-size limits
- Journey/search rate limits
- MOTIS request timeouts and cancellation
- Health endpoint
- Automatic restart
- Daily backup of configuration and irreplaceable small state

Acceptance:

- MOTIS is not directly exposed to the internet.
- Expensive parameters are clamped by the API.
- A process restart restores service without manual data repair.
- No MOT credential appears in logs, images, or client bundles.

### O4.3 — Privacy verification

**Estimate:** 0.5 day  
**Dependencies:** O4.2

Tasks:

- Disable or redact request-body logging for journey coordinates.
- Redact place queries from normal production logs.
- Confirm proxy/CDN configuration does not store request bodies.
- Define short operational-log retention.
- Verify no home/work/favourite data leaves the client.

Acceptance:

- A test journey leaves no precise origin/destination in normal application or proxy logs.
- Error telemetry contains request IDs and typed error data, not raw locations.

### O4.4 — Feed update without a platform

**Estimate:** 1 day  
**Dependencies:** D1.1, O4.2

Implement the smallest safe update flow:

```text
download → hash → validate → import candidate → run benchmark smoke subset
→ activate during a controlled restart/window → keep previous version for rollback
```

Phase 0 does not require zero-downtime dual-MOTIS swaps. A brief controlled restart is acceptable for dogfooding.

Acceptance:

- Invalid input leaves the previous working version active.
- One previous data version is retained.
- The update can be run manually before it is scheduled.
- Failure is visible in `/v0/health` or operator logs.

### V4.1 — Instrument operational and performance behavior

**Estimate:** 0.5 day  
**Dependencies:** O4.2

Record without precise location history:

- Request count by endpoint
- p50/p95/p99 latency by endpoint
- MOTIS duration separated from API duration
- Active and queued routing requests
- Request cancellation and timeout counts
- Typed error count
- Journey result count
- Realtime state distribution
- Feed age
- Match rate by operator/mode
- Snapshot build/activation duration and entity count
- Process CPU, memory, and restart count
- Client-side fatal errors

Do not record:

- Exact origin/destination pairs
- Continuous GPS
- Home/work labels
- User identity

Acceptance:

- Enough data exists to size and debug the service without building an analytics platform.
- Metrics use bounded labels; trip IDs, search terms, and coordinates are not metric dimensions.
- A slow journey can be attributed to the client, network, API, or MOTIS from available timing evidence.

### B4.1 — Run the deployed capacity and perceived-speed test

**Estimate:** 1 day  
**Dependencies:** O4.2, V4.1, B2.1, B3.1 when realtime is available

Tasks:

- Run the representative endpoint mix against the deployed host.
- Increase concurrency until a latency budget, error threshold, CPU limit, memory limit, or configured queue limit is reached.
- Run a short burst profile representing commute-time spikes.
- Test one realtime activation and one feed-degraded state during load.
- Measure client selection-to-useful-results time from a normal Israeli connection where practical.
- Compare deployed results with the local baseline.

Acceptance:

- The report states a tested operating envelope in requests/second and concurrency.
- The report identifies the first bottleneck and what scaling action would address it.
- It makes no conversion from requests/second to users without a measured per-session request model.
- The deployed app meets the latency budgets or clearly records the remaining gap before claiming speed as a differentiator.

### V4.2 — Five-day dogfood protocol

**Estimate:** 0.5 day setup plus normal usage  
**Dependencies:** O4.2, P3.1 or P2.3 if realtime is unavailable

During at least five calendar days:

- Run at least 20 journey searches.
- Follow at least three suggested journeys in the real world when practical.
- Include one intercity or multimodal journey.
- Compare unexpected results with schedule data and another planner.
- Record each time the developer opens another app and why.
- Record slow-feeling interactions and correlate them with client, network, API, and MOTIS timings.
- Record the actual requests generated by search, planning, detail, refresh, and app resume.

For every failure, classify:

- Search failure
- Routing failure
- Data-source failure
- Realtime mismatch
- Client comprehension problem
- Missing feature
- Performance problem

Acceptance:

- The dogfood log contains evidence, not only impressions.
- The top five blockers are ranked by frequency and severity.
- API changes required by the client are separated from future feature wishes.
- The real request-per-session model replaces the original five-requests-per-user assumption.

### Milestone 4 exit

- [ ] The client works on a real phone against a deployed or realistically networked environment
- [ ] Hosting is based on measured resources
- [ ] Rate limits and privacy redaction are verified
- [ ] Static feed update and rollback work
- [ ] Deployed operating envelope and perceived-speed measurements are published
- [ ] Five-day dogfood findings exist

## 11. Milestone 5 — Phase 0 decision

**Target:** Focused days 31–32  
**Visible result:** A signed decision about what to build next, based on the working vertical slice.

### V5.1 — Score the exit criteria

#### Product

- [ ] A user can search and plan a real journey from a phone.
- [ ] Journey detail communicates boarding, direction, transfers, and exit.
- [ ] At least 23/25 benchmark journeys are reasonable or failures are bounded and acceptable.
- [ ] At least three suggested journeys were followed or otherwise field-validated.
- [ ] Dogfooding identifies a credible reason to continue.

#### Search

- [ ] The 100-query corpus has measured top-1 and top-3 quality.
- [ ] Hebrew and English do not have systematic blocking failures.
- [ ] The chosen geocoding approach fits the measured host or has a costed next step.

#### Realtime

- [ ] The source and legal path are explicit.
- [ ] Match quality is measured by operator and mode.
- [ ] Realtime-aware routing versus annotation-only behavior is an explicit decision.
- [ ] The client truthfully handles partial, stale, and absent realtime.

If direct live access is still unavailable, Phase 0 may close with one of three explicit outcomes:

1. Continue with a named third-party realtime dependency.
2. Release a schedule-only MVP and narrow the product promise.
3. Stop or pause the product.

#### Engineering and operations

- [ ] Local startup is documented and reproducible.
- [ ] Full-stack memory, CPU, disk, and latency are measured.
- [ ] The deployed cost is known rather than estimated.
- [ ] Invalid static data cannot silently replace the active version.
- [ ] Exact journey coordinates are absent from normal logs.
- [ ] Expensive routing inputs are bounded.
- [ ] Static and realtime-enabled performance reports include full provenance.
- [ ] The deployed operating envelope and first bottleneck are known.
- [ ] End-to-end perceived speed is measured separately from server latency.
- [ ] Any unmet latency budget is explicit and blocks unsupported speed claims.

### V5.2 — Make one of four decisions

#### GO — expand the vertical slice

Use when the product works, data access is sustainable, and the top problems are ordinary implementation work.

Next phase focuses on:

- Client usefulness
- Search relevance
- Route presentation
- Stop departures
- Feed automation
- Contract stabilization from `/v0` toward `/v1`
- Performance-regression protection and optimization of measured bottlenecks

#### GO WITH CONDITIONS

Use when the static product works but a bounded dependency remains, such as MOT access or one operator's match quality.

Record:

- The exact condition
- Owner
- Deadline
- Allowed interim behavior
- What would cause the project to stop

#### PIVOT

Examples:

- Build a client on Transitous/Open Bus rather than host a complete backend.
- Focus on rail/intercity journeys.
- Ship schedule-only with excellent search and presentation.
- Contribute the SIRI adapter upstream instead of maintaining a proprietary integration layer.

#### STOP

Use when legal access, routing correctness, geocoding quality, or operational cost makes the intended product unviable.

### V5.3 — Replace assumptions in the long-term design

Update the broader PRD/system design only after the decision. Replace estimates with Phase 0 evidence for:

- Host memory and cost
- Routing latency and throughput
- Geocoder selection
- Realtime integration shape
- Match thresholds
- API contract
- Client platform choice
- Required infrastructure

Do not carry unvalidated latency, capacity, or component claims into Phase 1.

### V5.4 — Package the backend portfolio evidence

**Estimate:** 1.5 days  
**Dependencies:** V5.1, V5.2, V5.3

Create:

- A concise architecture overview centered on the measured hot path
- ADRs for routing engine, realtime integration, geocoder, runtime, and deferred infrastructure
- A reproducible benchmark guide
- Versioned static and realtime performance reports
- At least one CPU profile or flame graph for a meaningful bottleneck and the resulting decision
- Failure demonstrations for stale realtime, invalid GTFS, router timeout, and source unavailability
- An honest capacity/cost section with tested limits
- A short client demonstration showing perceived speed and truthful degradation
- A limitations section explaining what is intentionally not production-ready

Acceptance:

- A reviewer can understand the backend's boundaries, reproduce a representative benchmark, and see why the chosen optimizations exist.
- The portfolio tells a measurement-to-decision story rather than presenting a large component diagram as proof of skill.
- The minimal client remains evidence of a real product path, not the center of the portfolio narrative.

## 15. Risks and planned responses

| Risk | Early signal | Phase 0 response |
| --- | --- | --- |
| MOT never grants access | No useful response by decision date | Complete static MVP; choose third party, static pivot, or stop |

## 16. Expansion triggers after Phase 0

Infrastructure or complexity is added only when its trigger occurs.

| Addition | Trigger |
| --- | --- |
| Redis | A second live API instance or separate subscriber actually exists |
| Postgres/PostGIS | A required user/admin query cannot be served from MOTIS or versioned files |

| Photon/Elasticsearch | Fixed search corpus proves MOTIS plus small aliases insufficient |
| Custom stop index | Measured stop-search latency/relevance fails and MOTIS cannot be configured to pass |

| Blue/green MOTIS | Measured update downtime is unacceptable to real users |
| Second API host | Load or availability evidence, not forecast, requires it |
| Specialized cache or precomputation | A profile shows repeated deterministic work dominates a supported request path |
| Native mobile app | PWA validates product value and a required capability needs native APIs |
| Stable `/v1` | The real client contract stays stable through at least two dogfood iterations |
| Custom ranking | Measured journeys show MOTIS ordering repeatedly harms users |
| Reliability analytics | Enough lawful history exists and users value a defined reliability outcome |

## 17. Definition of done

Phase 0 is done when the project has all of the following:

1. A working minimal mobile-first client, not only an API demonstration.
2. A thin `/v0` API and internal domain model shaped by that client without leaking MOTIS or SIRI structures.
3. Full-feed routing measurements from actual Israeli data.
4. A fixed journey and search benchmark corpus with recorded correctness and relevance results.
5. Reproducible p50/p95/p99, throughput, error, CPU, and memory reports with full provenance.
6. A known deployed operating envelope and first saturated resource.
7. End-to-end perceived-speed measurements separated into client, network, API, MOTIS, and enrichment time where practical.
8. Profiles explaining at least one meaningful backend bottleneck or confirming that no custom optimization is yet justified.
9. A realtime source decision supported by measured reconciliation.
10. An explicit answer about whether MOTIS can own realtime routing.
11. A deployed cost measured from the selected host, or a documented reason to remain local.
12. At least five days of structured dogfooding and a measured request-per-session model.
13. A written go, conditional-go, pivot, or stop decision.
14. A portfolio package that lets another engineer reproduce and evaluate the backend claims.
15. A shorter Phase 1 plan based on observed problems rather than the dream architecture.

The best Phase 0 outcome is not the largest prototype or the busiest architecture diagram. It is the smallest working product that makes the next decisions obvious and proves its backend qualities with reproducible evidence.
